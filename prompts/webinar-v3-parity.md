## 0. What this is

`miles-masterclass-v3` renders the webinar landing page and detail page in four visual states — guest vs signed-in, and not-registered vs registered — with distinct layouts for each. `miles-masterclass` already has a webinar feature at `src/app/features/offerings/webinar/` (MIL-7 → MIL-11) bound to the Events v1 contract, but its templates are a first pass and only partly match v3. This plan brings the two pages to v3 design parity using the platform's folder rules (AGENTS.md §3), design tokens (`src/styles/styles.css`) and `shared/ui` kit, with every API shape typed against the Postman collection.

**Rules for the implementation:** reuse the existing feature — no new sub-feature, no new shared components, no new assets unless named in §6. No `.component` suffix, no `NgClass`, `@Service()` + `inject()`, ng-primitives only, Tailwind in templates, `httpResource` for reads + `HttpClient` for writes then `.reload()`, `@defer` only below the fold with a sized placeholder.

## 3. API contract (Postman, folder 06) — the single source of truth for types

All shapes below were checked against the request descriptions and every saved example. Note: the 200 examples are template-generated (`"<highlight>"` placeholders), so nullability comes from the contract tables, not the examples.

### 3.1 `GET web-api/v1/events/webinar-main-page/?login_type=pre_login|post_login`

Envelope `{ message: string; data: WebinarMainPageData }`. All five bucket keys always present (`[]` never omitted). `pre_login` ⇒ `completed_webinar` and `absent_webinar` are `[]`; `missed_webinar` **is** populated for guests. Buckets capped at 20, no pagination. `highlight_webinars` overlaps `upcoming_webinars` (dedupe on `id`). 400 `{status:'error', code:'invalid_request', errors: unknown[]}`; 401 (post_login without token) `{status, code:'authentication_required', message}`; bad token 403.

### 3.3 `GET web-api/v1/events/webinar-details-page/?webinar_id=<uuid>`

No `login_type` param (sending one is a 400 `extra_forbidden`); surface follows the token and is echoed as `data.login_type`. `data.webinar` = card + `description: string | null`, `trailer_url: string | null`, `trailer_thumbnail_url: string | null`, `product: { id; name; mini_description: string | null; description: string | null; horizontal_image; vertical_image; square_image } | null` (image strings `''` when unset). `registration` present only when authenticated; `eligible` never. 404 `{status, code:'webinar_not_found', message}` (note: `message` here, `detail` on the POST).

### 3.4 `POST api/v1/events/register-via-zoom/` body `{ webinar_id: string }` (only key; JWT required)

- 200 `{ status:'already_registered'; code:'already_registered'; message: string; booking_id: string }`
- 202 `{ status:'accepted'; registration_status: RegistrationStatus; message: string; attempt_id: string; status_url: string }` (relative path; "Registration already in progress." when an attempt is in flight)
- 400 `invalid_request` (`errors[]`) · 400 `missing_email | invalid_email | missing_first_name | invalid_first_name` (`detail`) · 400 strict-key map `Record<string,string>` · 403 `{ detail }` · 404 `webinar_not_found` (`detail`) · 409 `registration_in_progress` (`detail`, `retry_after_seconds: number` = 15) · 409 `unsupported_webinar_type | webinar_cancelled | webinar_inactive | webinar_start_time_missing` (`detail`).

### 3.5 `GET api/v1/events/register-via-zoom-status/{attempt_id}/` (no query, JWT)

200 `{ attempt_id: string; status: InternalAttemptStatus; registration_status: RegistrationStatus; zoom_attempts: number; last_status_code: number | null; error_message: string | null; error_code: string | null; mf_retry_count: number; join_url: string | null; registered_email: string | null; booking_id: string | null; completed_at: string | null }`. Unknown `status` ⇒ treat as `PENDING`. `ZOOM_PENDING_APPROVAL` is terminal-but-PENDING ⇒ cap polling (2 s × 15 s, then back off, cap 30–45 s). A reaped worker returns `INTERRUPTED`/`REGISTER` with `error_code:'stuck'`. 404 `attempt_not_found`.

### 3.6 Auth (folder 01) — used by the guest "Secure Your Seat" card

`POST api/v1/account/auth-identify/ {identifier}` → `{ methods, defaultMethod, communicationId | null, … }` (render `methods`, don't assume OTP); `POST auth-otp-send/ {identifier}` → `{ channel: 'email'|'sms'|'whatsapp'; cooldownSeconds: number }`; `POST auth-otp-verify/ {identifier, code}` → `{ accessToken; refreshToken; profile_status: 'new_user'|'onboard_completed'|'profile_completed'; is_test_user: boolean }`. 401 wrong code · 429 locked · 403 `account_blocked | account_deactivated`. All already typed in `core/models/auth.model.ts` (`AUTH_ROUTES`, `SessionResponse`) and driven by `AuthSession.sendOtp/verifyOtp`.
